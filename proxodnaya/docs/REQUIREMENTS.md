# Требования (FR / NFR) и трассировка к критериям

Приоритеты: **P0** — допуск или защита от снятия, без этого ноль баллов. **P1** — основные баллы. **P2** — бонусы, только после закрытия P0+P1 (бонусы засчитывают лишь при полностью закрытом обязательном объёме).

> ⚠️ Сценарии С1–С22 и разделы 5.3/5.5 описаны в тексте кейса, которого у нас пока нет. Привязка к С-номерам ниже — гипотеза. Получим кейс — сверим и поправим этот файл.

## H. Чек-лист «не снимут» (прогоняем перед защитой)
- [ ] В клиентском коде нет логики решения о проходе (grep `allow` во frontend)
- [ ] Чужое лицо + чужой QR → отказ `FACE_MISMATCH`
- [ ] Фото человека на телефоне перед камерой → отказ по живости
- [ ] Скриншот QR через 2 мин → `QR_EXPIRED`; повтор того же QR → `QR_REUSED`; QR с выключенным на телефоне интернетом → проход работает
- [ ] `docker compose restart` → журнал, смены и люди на месте
- [ ] `docker compose stop face` → проход DENY `SYSTEM_ERROR`, не ALLOW
- [ ] `docker compose stop shift` → проходы работают; после старта интервалы догнались из Kafka
- [ ] Чистая БД → дашборд показывает нули/«нет данных», а не красивые графики
- [ ] Вопрос помощнику про несуществующие данные → «таких данных нет», без выдуманных чисел
- [ ] `LLM_PROVIDER=ollama` → помощник отвечает с выключенным интернетом
- [ ] `gitleaks detect` по всей истории — чисто
- [ ] Каждый из 5 рассказывает свой модуль за 60 с
