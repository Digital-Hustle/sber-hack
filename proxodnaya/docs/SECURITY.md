# Безопасность

Безопасность — главный акцент решения: блок «Надёжность прохода» стоит 28 баллов, а половина оснований для снятия про безопасность.

## 1. Модель доступа
| Кто | Как входит | Факторы | Роли |
|---|---|---|---|
| Администратор, руководитель, офицер безопасности | **Keycloak SSO** (OIDC Authorization Code + PKCE) | пароль + **TOTP** (обязательно для ADMIN и SECURITY_OFFICER) | ADMIN, MANAGER, SECURITY_OFFICER |
| Охранник на киоске | Keycloak SSO (тот же realm — один вход на админку и киоск) + **ключ устройства киоска** | пароль + ключ устройства (WebCrypto) | GUARD |
| Рабочий | **без пароля**: ключ устройства (ECDSA P-256, неизвлекаемый, WebCrypto), выданный при активации по инвайту | телефон (ключ) + лицо на проходной + живость | WORKER |
| Сервисы | service account в Keycloak (client credentials) | client secret из `.env` | — |

Почему у рабочих нет Keycloak-пароля: на стройке пароли забывают и передают друзьям. Ключ устройства нельзя скопировать, а лицо и живость на проходной дают второй и третий фактор. Backend принимает JWT двух издателей: Keycloak (персонал) и внутренний `gate-device` (рабочие, короткоживущие ES256-токены после challenge-подписи ключом устройства). В Spring для этого есть `JwtIssuerAuthenticationManagerResolver`.

## 2. Keycloak
- Realm `proxodnaya` импортируется при старте из `infra/keycloak/realm-proxodnaya.json`. Все секреты в нём — плейсхолдеры `${ENV}` (Keycloak подставляет переменные окружения при импорте). В git нет ни одного реального секрета.
- Клиенты:
  - `gate-admin` — public, PKCE, redirect `https://<host>/admin/*`;
  - `gate-kiosk` — public, PKCE, redirect `https://<host>/kiosk/*`;
  - `gate-api` — audience для backend, bearer-only;
  - `gate-provisioner` — confidential, service account с ролью `manage-users` (backend создаёт персонал из админки).
- Роли realm: `ADMIN`, `MANAGER`, `SECURITY_OFFICER`, `GUARD`. Маппер ролей кладёт `realm_access.roles` в токен. Конвертер в Spring превращает их в `ROLE_*`.
- Политики:
  - пароль от 12 символов, не равен логину;
  - **Brute Force Detection** включена;
  - access token 5 мин, refresh — с ротацией, SSO idle 30 мин;
  - required action `CONFIGURE_TOTP` для ADMIN и SECURITY_OFFICER.
- Журнал событий Keycloak (login, login_error) включён. Неудачные входы видны офицеру безопасности.
- **SSO**: один realm на админку и киоск, вход один раз. Логаут — RP-initiated logout.
- **Внешние IdP (P2)**: брокеринг «Войти через Яндекс ID / GitHub» для персонала. Это демонстрация федерации. Sber ID и ЕСИА требуют договора — на защите говорим, что они подключаются тем же OIDC-брокером без изменения кода.

## 3. Модель угроз (STRIDE-lite) → защита → как проверить
| # | Угроза | Защита | Проверка (демо/тест) |
|---|---|---|---|
| T1 | Пройти по чужому телефону/QR | сверка лица 1:1 с владельцем токена, порог τ | `FACE_MISMATCH` |
| T2 | Поднести фото/видео владельца | активный челлендж живости + сверка по всем кадрам; MiniFASNet (P2) | `LIVENESS_FAILED` |
| T3 | Скриншот или пересылка QR | Окно 30 с (допуск ±90 с), одноразовость через `qr_uses`, атомарное гашение, подпись неизвлекаемым ключом устройства | `QR_EXPIRED` / `QR_REUSED` / `DEVICE_REVOKED` |
| T4 | Подделать ответ «пропустить» на клиенте | решение только на сервере; киоск лишь показывает ответ сервера | grep фронта, код DecisionEngine |
| T5 | Повторить перехваченный запрос киоска | подпись запроса ключом киоска + nonce + метка времени (окно 30 с) | тест replay |
| T6 | Перебор лица/токенов | rate-limit по рабочему, киоску и IP; временная блокировка; оповещение | `TEMP_LOCKED` |
| T7 | Подбор пароля админа | Keycloak brute force + TOTP | 5 неудачных входов → блок |
| T8 | Кража сессии админа | короткий access token, ротация refresh, токены только в памяти (не в localStorage), CSP | заголовки в DevTools |
| T9 | Повышение прав (WORKER → ADMIN API) | `@PreAuthorize` на каждом эндпоинте + тест «каждый эндпоинт × каждая роль» | матричный тест |
| T10 | IDOR (чужие данные по id) | WORKER видит только себя, проверка владельца в сервисе | тест |
| T11 | Утечка биометрии из БД | AES-256-GCM шифрование фото и эмбеддингов (ключ в `.env`), доступ только ADMIN, аудит просмотров | `SELECT` показывает шифротекст |
| T12 | Незаметная правка журнала | hash-chain: `hash = SHA-256(prev_hash ‖ запись)`, кнопка «Проверить целостность», БД-роль приложения без UPDATE/DELETE на журнал | правим строку руками → проверка показывает разрыв |
| T13 | Секреты в git | `.env` в `.gitignore`, плейсхолдеры в realm, gitleaks в pre-commit и CI | `gitleaks detect` |
| T14 | Уязвимые зависимости | Trivy fs-скан в CI, Dependabot | отчёт CI |
| T15 | Prompt injection в помощнике (ФИО «игнорируй инструкции…») | модель видит только результаты инструментов, инструменты read-only, валидатор чисел, роль MANAGER+ | тест с вредоносным ФИО |
| T16 | Отказ модели или лица | fail-closed для прохода, circuit breaker для LLM | выключить Ollama → проходы работают |
| T17 | SQL-инъекции, XSS | JPA/параметры, React-экранирование, CSP без `unsafe-inline` | — |

## 3.1 Межсервисная безопасность
- Наружу только Caddy → gateway и Keycloak. Сервисы и Kafka — во внутренней сети без проброса портов.
- Каждый сервис валидирует JWT сам (defense in depth). Межсервисные вызовы — токены service account с `aud`.
- `/internal/**` эндпоинты доступны только с ролью `SVC_<caller>`.
- Отдельные роли PostgreSQL на сервис; Kafka без внешнего порта, `auto.create.topics=false` (SASL/ACL на сервис — при наличии времени).
- Офлайн-QR (ADR-028): подпись ECDSA ключом устройства, на сервере только публичные ключи; повтор блокирует уникальность `(device_id, window)`. Офлайн-снимок для киоска подписан сервером и живёт 12 ч (ADR-029).
- Угрозы: T18 — компрометация одного сервиса → доступ только к его БД и очередям; T19 — подделка события в шине → права publish только у владельца exchange, consumer проверяет `producer`.

## 4. Транспорт и заголовки
- Только HTTPS (Caddy, Let's Encrypt), HSTS.
- CSP: `default-src 'self'; connect-src 'self' https://auth.<host>; img-src 'self' blob: data:; frame-ancestors 'none'`.
- `X-Content-Type-Options`, `Referrer-Policy: no-referrer`, `Permissions-Policy: camera=(self), geolocation=(self)`.
- CORS: только свои origin.

## 5. Данные и ПДн (152-ФЗ — плюс на защите)
- Минимизация: храним ФИО, табельный номер, подрядчика, должность, биометрию (зашифрованную), события.
- Согласие на биометрию — чекбокс при заведении, фиксируется в аудите.
- Удаление рабочего удаляет биометрию. События обезличиваются (остаётся id), агрегаты сохраняются.
- Логи без ПДн: маскирование ФИО, фото и эмбеддинги не логируем.

## 6. Аудит
- `audit_log`: кто (sub из JWT), что, когда, откуда (IP), до/после — для всех действий админа и просмотров биометрии.
- Страница «Безопасность» (SECURITY_OFFICER): аудит, события входа Keycloak, проверка целостности журнала, статистика отказов по причинам.

## 7. Чек-лист безопасности перед защитой
- [ ] Матричный тест ролей зелёный
- [ ] Проверка целостности журнала: «OK», после ручной правки — «разрыв на записи N»
- [ ] В БД биометрия зашифрована
- [ ] TOTP у админа включён
- [ ] `gitleaks detect` и Trivy чисто
- [ ] CSP и заголовки на месте (securityheaders-подобная проверка curl'ом)
