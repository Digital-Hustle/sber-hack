# Защита: сценарий, матмодель, вопросы — «Документы»

Формат (п. 7.6): презентация + **математическая модель** + демонстрация. Судьи проверяют сами, на нашем стенде. Готовим «маршрут судьи». Сценарии С1–С22 уточнить по тексту кейса (PLT-00).

## Маршрут судьи (распечатка на столе)
1. Телефон судьи → `https://<host>/apply` → согласие → анкета: «Узбекистан» → список из 5 документов с пояснениями; меняем на «Казахстан» → патент исчез (С1–С2).
2. Фото паспорта и патента камерой телефона → мгновенно «принят» → стадии идут сами (С3, Д7).
3. Положить патент в пункт «паспорт» → «Это патент — перенесли».
4. Пустой файл, `.exe` переименованный в `.jpg`, PDF с паролем, тот же файл второй раз → внятные отказы (С3–С6).
5. Размытое фото → «Снимок размыт, держите телефон неподвижно» (С9).
6. Оператор → вход через Keycloak → очередь → карточка: скан слева, поля справа, клик по полю подсвечивает место на скане; сомнительные поля сверху (С13–С16).
7. Правка поля → история: кто, когда, было/стало (B-08). «Вернуть на доработку» → соискатель видит запрос (С17–С18).
8. Расхождение ФИО паспорт ↔ патент → замечание (B-03). Метрики очереди (B-06).
9. Устойчивость: загрузить 10 файлов разом → идут параллельно; `docker compose restart docproc` посреди разбора → доделано; `stop ollama` → «приостановлено», `start` → догнал (С10–С12).
10. Закрытость: выйти из оператора, открыть ссылку на карточку/файл → вход/401 (Д8).
11. Локальная модель: `LLM_PROVIDER=ollama`, интернет выключен → разбор работает (С19–С20, Д6).
12. Репозиторий: история, docs, DECISIONS, EVAL-отчёт, `gitleaks` чисто.

## Сценарий «соискатель → оператор» (пошагово, на стенде)
Демо-пользователи Keycloak (realm `documents`, `infra/keycloak/realm-documents.json`; пароли — в `infra/.env`, генерирует `scripts/gen-env.sh`):

| Логин | Пароль из `.env` | Роль | Что может |
|---|---|---|---|
| `operator` | `KC_DEMO_OPERATOR_PASSWORD` | OPERATOR | очередь, «Взять следующую», карточка, правка полей и типа, подтверждение, запрос «переснять», решение |
| `senior` | `KC_DEMO_SENIOR_PASSWORD` | OPERATOR + SENIOR_OPERATOR | всё, что operator, + «Разобрать заново», выгрузки DOCX/XLSX, отчёт по истекающим |
| `auditor` | `KC_DEMO_AUDITOR_PASSWORD` | AUDITOR | только чтение: список заявок, история, метрики (ПДн замаскированы) |

**Соискатель (телефон, 390×844)**
1. `https://<host>/apply` → согласие на обработку ПДн → заявка создана; ссылка вида `/apply/<id>#k=…` и код возобновления. Ключ сразу убирается из адресной строки и живёт только в этой вкладке — «Скопировать ссылку», чтобы вернуться.
2. Анкета (гражданство, цель, срок) → чек-лист обязательных и «по желанию» документов.
3. В пункт «Паспорт РФ» — фото или PDF (кнопка камеры открывает системную камеру, снимок сжимается до 4 МП). Файл принят сразу, дальше стадии идут сами по SSE: текст → тип → поля → проверки.
4. Положить документ не в свой пункт → «Это „…“ — перенесли в нужный пункт». Размытый снимок → «Снимок размыт» с подсказкой и кнопкой «Переснять».
5. «Отправить» (или «Отправить то, что есть» с перечнем недостающих) → заявка уходит в очередь.

**Оператор (ноутбук)**
6. `https://<host>/operator` → вход `operator` → очередь: статус, ожидание, «есть что перепроверить»; «Взять следующую» (N).
7. Карточка: скан слева, поля справа, сомнительные сверху. J/K — по полям, клик или «Показать» → подсветка места на скане, E — правка, Enter — подтвердить документ. Сверху — расхождения между документами (ФИО паспорт ↔ ИНН) и счётчик «Сэкономлено, мин».
8. Правка поля → вкладка «История»: кто, когда, было/стало. «Запросить» → соискатель видит «Оператор просит: переснимите …» в кабинете.
9. «Решение» → принять / отклонить с комментарием.
10. Выйти, войти `senior` → «Разобрать заново», DOCX/XLSX, «Истекающие». Войти `auditor` → метрики очереди с «как посчитано», ПДн скрыты, кнопок правки нет.
11. Перезагрузка страницы оператора → снова вход (токены только в памяти), Keycloak пускает по SSO без пароля.

## Математическая модель (1–2 слайда)
Полная версия с числами — [MATH.md](MATH.md); слайды — `docs/slides/documents-defense.pptx` (исходник `docs/slides/build_deck.mjs`, сборка `node build_deck.mjs`).

- **Уверенность поля**: c = w₁·c_model + w₂·c_ocr + w₃·c_checks; калибровка — P(поле верно | c ∈ корзина) на открытом и своём наборе; порог τ выбираем, минимизируя время оператора T = N_review·t_check + N_errors_missed·t_fix при ограничении «пропущенных ошибок ≤ ε».
- **Классификация**: argmax по типам с порогом θ; ниже θ → `UNKNOWN` (стоимость неверного типа ≫ стоимости ручной проверки).
- **Контрольные суммы**: MRZ — Σ dᵢ·wᵢ mod 10, wᵢ ∈ (7,3,1); СНИЛС — Σ dᵢ·(10−i) mod 101; ИНН — две цифры mod 11 mod 10. Вероятность, что случайная ошибка OCR пройдёт проверку MRZ ≈ 1/10 на поле, на трёх полях ≈ 10⁻³.
- **Очередь**: M/M/c, λ — поток документов, μ — 1/среднее время разбора, c = число воркеров (ограничено семафором модели); ожидание W_q по формуле Эрланга C → почему 4 воркера и лимит 2 вызова к локальной модели.
- **Честность метрики очереди**: среднее и p95 времени по стадиям из `stage_events`, а не «оценка».

## Структура слайдов (≤ 7)
1. Проблема: фото в мессенджере, ручная перепечатка, непригодные снимки
2. Решение и два интерфейса (скрины)
3. Конвейер: приём → очередь в БД → текст → тип → поля → проверки (схема)
4. Качество: как меряли, без подгонки (EVAL), матмодель уверенности
5. Модель: изоляция, локальный запуск, выбор по замеру
6. Безопасность и ПДн, инженерия
7. Команда и кто за что отвечал
