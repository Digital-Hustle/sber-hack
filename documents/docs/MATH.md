# Математическая модель — «Документы»

Четыре вопроса, на которые модель отвечает числом: насколько верить полю, когда звать оператора, сколько стоит ошибка распознавания и сколько ждать в очереди. Параметры — из `services/docproc/src/main/resources/application.yml`; всё, что помечено «пример», считается заново по `stage_events` и `eval/` на реальном стенде.

## 1. Уверенность поля (ADR-011, `rules/ConfidenceScorer`)

c = min(1, w_m·c_model + w_o·c_ocr + w_k·c_checks), w_m = 0,4, w_o = 0,3, w_k = 0,3

- c_model — самооценка модели по полю (0..1), c_ocr — средняя уверенность Tesseract по словам, где код нашёл значение на скане (`WordLocator`; не нашёл — штраф), c_checks — 1, если все проверки поля прошли, 0 — если есть провал, 0,7 — если проверок у поля нет.
- Поле уходит оператору наверх, если c < τ = 0,8, или проверка провалена, или обязательное поле не найдено.

| Пример | c_model | c_ocr | проверки | c | Итог |
|---|---|---|---|---|---|
| СНИЛС, контрольное число сошлось | 0,90 | 0,85 | пройдены | 0,915 | автоматически |
| СНИЛС, контрольное число не сошлось | 0,90 | 0,85 | провал | 0,615 | оператору, `CHECKSUM_FAILED` |
| ФИО (проверок нет) | 0,90 | 0,85 | — | 0,825 | автоматически |
| ФИО, слово плохо распознано | 0,90 | 0,40 | — | 0,690 | оператору |

Почему так: модель склонна переоценивать себя, поэтому её вес меньше половины, и одной её уверенности не хватает для порога (0,4 < 0,8). Даже при c_model = 1 поле уходит оператору, если текст на скане не найден или проверка не прошла.

## 2. Порог τ и калибровка (DP-16)

Выбираем τ, минимизируя время оператора при ограничении на пропущенные ошибки:

T(τ) = N_review(τ)·t_check + N_missed(τ)·t_fix → min, при условии N_missed(τ)/N ≤ ε

- t_check ≈ 10 с (посмотреть поле с подсветкой на скане), t_fix ≈ 10 мин (найти и исправить ошибку после решения), ε = 1 %.
- Калибровка: делим поля открытого набора на корзины по c, в каждой считаем долю верных P(верно | c). Модель откалибрована, если P ≈ c. Веса w подбираем на половине набора (логистическая регрессия «верно/неверно» по трём признакам), τ и проверку — на второй половине, чтобы не подогнать.
- Статус: открытого размеченного набора в репозитории нет → калибровка не проведена, веса — экспертные. Скрипт прогона и метрики готовы (`eval/run.py`, EVAL.md).

## 3. Вид документа

type = argmax P(тип | текст, признаки); если max < θ = 0,6 или модель ответила UNKNOWN → `TYPE_UNKNOWN`, оператор выбирает вид.

- Стоимость неверного типа (все поля извлечены по чужой схеме) намного выше стоимости ручного выбора, поэтому θ консервативный.
- Уверенность модели штрафуется кодом: если «доказательства» (`evidence`) не найдены в тексте документа — ×0,6, иначе ×(0,8 + 0,2·доля найденных).
- Многостраничный файл (DP-14): модель размечает страницы по документам, код проверяет разметку; поля берутся только со страниц основного документа.

## 4. Контрольные суммы: сколько ошибок OCR ловит код

| Проверка | Формула | Одна неверная цифра | Случайная строка пройдёт |
|---|---|---|---|
| MRZ (ICAO 9303) | Σ dᵢ·wᵢ mod 10, w = 7, 3, 1 | ловится всегда (7, 3, 1 взаимно просты с 10) | 1/10 на поле, ≈ 10⁻³ на трёх полях + общая сумма |
| СНИЛС | Σ dᵢ·(10 − i) mod 101 (100 → 00) | ловится всегда (веса 1..9 < 101, 101 — простое) | ≈ 1/100 |
| ИНН физлица | две контрольные цифры, mod 11 mod 10 | ловится почти всегда | ≈ 1/100 |

Поэтому «проверка прошла» поднимает уверенность (c_checks = 1), а провал — честный сигнал оператору, а не повод «поправить» значение автоматически.

## 5. Очередь разбора (M/M/c)

Документы приходят потоком λ, обрабатываются воркерами docproc (4) с лимитом одновременных вызовов модели c = 2 (`LLM_MAX_CONCURRENCY`). Узкое место — модель, поэтому считаем M/M/c с c = 2.

- μ — документов в минуту на один слот модели. Пример: два вызова модели (тип + поля) ≈ 20 с на документ на CPU → μ = 3 док/мин.
- Загрузка ρ = λ / (c·μ); ожидание в очереди W_q = C(c, λ/μ) / (c·μ − λ), где C — формула Эрланга C (вероятность ждать).

Пример (μ = 3 док/мин):

| λ, док/мин | c = 1 | c = 2 | c = 3 | c = 4 |
|---|---|---|---|---|
| 1,0 | ρ 0,33 · W_q 10 с | ρ 0,17 · 1 с | ρ 0,11 · 0 с | ρ 0,08 · 0 с |
| 2,5 (30 соискателей/ч × 5 док) | ρ 0,83 · 100 с | ρ 0,42 · 4 с | ρ 0,28 · 1 с | ρ 0,21 · 0 с |
| 4,0 | перегрузка | ρ 0,67 · 16 с | ρ 0,44 · 2 с | ρ 0,33 · 0 с |
| 5,5 | перегрузка | ρ 0,92 · 105 с | ρ 0,61 · 6 с | ρ 0,46 · 1 с |

Выводы: (1) c = 2 держит поток до ~4 док/мин с ожиданием меньше 20 с; (2) рост c на одной машине с CPU не даёт выигрыша — модель делит те же ядра, μ падает; масштабирование — GPU или облачный провайдер (μ × 5–10); (3) при ρ → 1 ожидание растёт нелинейно, поэтому в метриках оператора виден не «прогноз», а измеренные среднее и p95 по стадиям (`stage_events`, B-06).

## 6. Сколько времени экономит оператор

Сэкономлено = (N_полей − N_исправленных) · t_ввод, t_ввод ≈ 20 с на поле (перепечатать вручную). Поля, которые оператор исправил, экономии не дают. Счётчик «Сэкономлено, мин» в карточке заявки считает именно так по фактическим полям (`pages/operator/ui/ApplicationPage.tsx`); t_ввод — оценка, уточняется хронометражем.
