# PRD — intake

Продукт целиком — `../../../docs/PRD.md`, требования с ID — `../../../docs/REQUIREMENTS.md`. Здесь — только этот модуль.

## Обзор
Всё, что касается соискателя и входящих файлов: заявка и анкета, набор обязательных документов, приём файла с серверными проверками, дубликаты, дозагрузка и замена, хранение файлов в PostgreSQL зашифрованными, выдача стадий по SSE. **Мгновенный ответ** — разбор идёт в docproc в фоне (Д7).

## Проблемы
- Проверки на клиенте не считаются (Д1) — любой файл должен пройти серверные проверки, иначе СН.
- Соискатель загружает «что попало»: пустые, битые, переименованные, запароленные, огромные, повторные файлы.
- Набор документов зависит от гражданства/цели — нельзя показывать всем одинаковый список.
- Файлы — ПДн: хранить нельзя в открытом виде, на диске или в MinIO (лицензия).

## Цели
1. Каждый отказ — код + текст + подсказка (API.md), ни одного 500 на «плохой» файл (С3–С6, 12 баллов).
2. `202 Accepted` p95 ≤ 300 мс: файл + документ + outbox в одной транзакции.
3. Файлы и состояние переживают рестарт (Д3): всё в PostgreSQL.
4. Набор документов — данные (`doc_requirements`), а не `if` в коде (ADR-010).

## Пользователи
- Соискатель — через зону `/apply` (ключ заявки).
- docproc — забирает файлы через `/internal/intake/files/{id}`.
- review/оператор — содержимое файлов через `GET /intake/api/v1/files/{id}/content` (роль + аудит).

## Ключевые функции
- Создание заявки → ключ (256 бит, в БД только hash) + код возобновления.
- Анкета (гражданство, цель, срок) → `requiredTypes` из `doc_requirements`.
- Проверки: не пустой, размер, сигнатура (magic bytes, не расширение), целостность (PDF открывается, изображение декодируется), пароль PDF, число страниц, разрешение, MIME; sha256 и pHash для дубликатов.
- Версии файлов (`document_files.version`), дозагрузка страниц, замена, удаление.
- Хранение `content_enc bytea` AES-256-GCM, ключ `FILES_ENCRYPTION_KEY` из env.
- SSE `/applicant/applications/{id}/stream` — стадии из `docproc.document.v1`, итог «комплект полный / не хватает».
